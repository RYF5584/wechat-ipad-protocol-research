## 这次更新是干什么的

这篇记录主要是跟进微信「死号强开」(self_deblock / unban) 这条链路在新版本里的变化。

老版本的强开相对简单：拿到 `ticket` 以后，过一道腾讯滑块(appid `2000000008`)，再按 `verifycode → moneytransfer` 这几步往下走，基本就能把账号解封限制推进下去。整条链路只依赖 `ticket`，不需要额外准备设备侧的安全材料。

但新版本这条链路变了：服务端在强开校验里新增了对 **ccdata 算法** 的校验，同时也要求带上 **mmsf0001 对应的 SecurityInfo**。也就是说，原来「只要过滑块就能强开」的思路已经不成立了。

## 它最终是为了解决什么事情

这次更新解决的是：

- 新版微信死号强开链路里，单纯过滑块已经不够，必须同时准备 ccdata 和 SecurityInfo 才能继续往下走
- 这两段材料都和设备侧强相关，不能像老版本那样只靠一个 `ticket` 就跑通

如果不把这件事理清楚，常见现象就是：

- 滑块明明过了，`verifycode` 这一步却过不去
- 或者滑块过了、`ret` 也对，但后续步骤报错退回
- 根本原因不在滑块本身，而在于设备安全材料没补齐

## 关键变化

新老版本的核心区别可以简单理解为：

```text
旧版强开 = ticket + 过滑块
新版强开 = ticket + 设备材料(ccdata) + SecurityInfo(mmsf0001) + 过滑块
```

具体来说：

- **ccdata**：现在强开校验里多了一段对 ccdata 算法的校验。这段数据需要从设备信息里按特定算法生成，并不是随便拼一段就能过的。
- **SecurityInfo**：这一段就是前面 `mmsf0001` 研究里一直在跟进的安全载荷。新版强开里它成了必带参数，没有它整条链路走不下去。

所以这次更新公开层面的结论很直接：

- 新版微信死号强开，已经把 ccdata 算法和 mmsf0001(SecurityInfo) 都纳入了校验
- 这意味着强开链路和前面登录安全验证链路，在设备安全材料这一段是相通的

## 现在已经能做到什么

现阶段，这条链路已经能够：

- 区分新老版本强开的差异，不再按老思路硬试
- 从设备材料侧同时准备 ccdata 和 SecurityInfo
- 把「过滑块」和「补设备安全材料」拆成两件独立的事来联调
- 在新版校验下继续推进强开流程，而不是卡在滑块之后的步骤
