## 这次更新是干什么的

这篇记录主要跟进账号密码(A16 / 62 数据)登录命中「新设备安全验证」后的整条链路，重点是把 `loginprecheck` 滑块和后续验证方式的获取这两段接通。

短信登录不像扫码那样扫完基本就进去了。账号密码登录在新设备场景下，经常会命中安全验证，而且这个验证是分多段的：先是 `loginprecheck` 这一道滑块，过了之后才会真正下发短信，短信还要再确认。如果第一道滑块没过，后面发短信这一步根本走不动。

这次更新就是围绕这两段来做的：

- 一段是**纯协议把 `loginprecheck` 滑块过掉**，让短信能真正发出去
- 另一段是**把验证方式(扫码 / 短信 / 其他)统一获取并承接**，让后续可以继续往下走

## 它最终是为了解决什么事情

这次更新解决的是：

- 账号密码登录命中新设备安全验证时，第一道 `loginprecheck` 滑块过不去，导致短信发不出去
- 验证方式返回的格式不统一，扫码、短信、其他分支很难用一套逻辑承接

如果不把这两段接通，常见现象就是：

- 明明走的是短信登录，但短信一直收不到，因为前面 `loginprecheck` 滑块没过
- 服务端返回的验证方式是扫码、短信、还是别的，结构各不一样，没法统一处理
- 验证做到一半，缺少统一的上下文承接，后续确认走不下去

## 研究思路

这条链路的研究思路可以拆成两段看：

```text
1) loginprecheck 滑块:
   生成 securityInfo -> login_captcha_cgi -> commverifycodecgi -> tcaptcha 滑块 -> verify_capt
   过了之后, 用同一台设备重发短信才能成功下发

2) 验证方式获取:
   precheck -> get_verify_method -> commit_choice(选择 action) -> get_verify_id -> 后续确认
   按返回 Type(qrcode / sms / raw) 分支承接
```

这里有几个关键点：

- **`loginprecheck` 滑块是纯协议完成的**：不需要走网页人工，由设备 ID 自动生成 `securityInfo`，把整条 cgi 链路跑通。这和前面 `mmsf0001 / securityInfo` 的研究方向是直接衔接的——滑块这一段同样依赖设备侧的 `securityInfo`。
- **必须用同一台设备**：过滑块和发短信要用同一个设备 ID(支持 32 位设备 ID / A16 / 62 数据自动识别)，否则即使滑块过了，换一台设备发短信还是发不出去。
- **验证方式统一承接**：扫码(`action=8`)、短信(`action=13`)、其他方式，返回结构不一样，这里统一成 `Data.Type` 来区分(qrcode / sms / raw)，具体数据统一包在 `Data.Data` 里，方便后续按分支处理。

短信这一段还区分上行和下行：

- 上行短信：用户用绑定手机号**发送**指定内容到指定号码，发送完再调接口确认
- 下行短信：用户**接收**验证码，收到后回填验证码确认

## 现在已经能做到什么

现阶段，这条链路已经能够：

- 纯协议把 `loginprecheck` 滑块过掉，让短信登录的短信能真正下发
- 统一获取并区分扫码 / 短信 / 其他验证方式，按 `Type` 分支承接
- 支持上行短信(发送后确认)和下行短信(收码后回填)两种确认方式
- 复用设备 ID 自动生成 `securityInfo`，不再需要网页人工接滑块
- 把「过滑块」和「验证方式承接」两段整理成可独立联调的能力
